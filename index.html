Technical Deep Dives

📅 Jul 2026 🏷️ Web Security 🔗 OverTheWire Natas Level 27

MySQL VARCHAR Truncation Exploit

  • Observation: MySQL ignores trailing spaces in VARCHAR unique-comparisons but stores them distinctly — creating a mismatch between WHERE and INSERT.
  • Exploit: Crafted a 65-char username (natas28 + 57 spaces + 'x'). PHP's substr(0,64) truncates the 'x', leaving natas28 + trailing spaces stored in the DB.
  • Outcome: Logged in as natas28 with my own password; dumpData() with trim() returned the real user's row — leaked the next password.
  • Defense: Use VARBINARY for usernames, trim input before any comparison, and reject whitespace-only differences in unique fields.
📅 Jul 2026 🏷️ Linux Privilege Escalation 🔗 OverTheWire Bandit

Linux PrivEsc via Cron & SetUID Binaries

  • Observation: Multiple Bandit levels involve cron jobs running as root, or setuid binaries that allow arbitrary command execution.
  • Exploit: Identified writable cron scripts, injected reverse shells, exploited nmap --interactive, and abused tar wildcard injection.
  • Outcome: Escalated from low-privilege user to root across multiple levels, capturing flags.
  • Defense: Avoid setuid on custom scripts; use cron path sanitization; never run tar with wildcards on untrusted directories.

Think-Aloud Walkthroughs

My methodology follows a repeatable loop: recon → hypothesize → test → pivot. Here's how I approached two very different challenges.

Scenario: MySQL Truncation (Natas 27)

Step 1 — Read the source code

I noticed substr($usr, 0, 64) in createUser() and trim($usr) in dumpData() — an inconsistency. validUser() used raw input. Classic sign of a truncation bug.

Scenario: MySQL Truncation (Natas 27)

Step 2 — Form a hypothesis

"If I push a 65-char username past the 64-char limit, the 65th character gets chopped during INSERT. But MySQL's WHERE still matches on the truncated value due to trailing-space insensitivity. I can create a duplicate user with my own password."

Scenario: MySQL Truncation (Natas 27)

Step 3 — Test and pivot

Sent POST username=natas28+57spaces+x&password=password. User created. Then logged in as natas28 — checkCredentials matched my fake user, dumpData with trim() returned the original natas28's row. Flag captured.

Scenario: Linux Escalation (Bandit)

Step 1 — Recon

Ran ls -la, find / -perm -4000, checked /etc/crontab and writable directories. Found a setuid binary or a cron job running my user's script.

Scenario: Linux Escalation (Bandit)

Step 2 — Exploit

Leveraged the setuid binary to execute commands as the target user, or modified the cron script to copy the next level's password. Verified with whoami and cat.
