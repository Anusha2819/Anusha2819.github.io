Pillar 2 · Proof I Can Investigate, Break & Defend

Technical Deep Dives

📅 Jul 2026🏷️ Web Security🔗 OverTheWire Natas Level 27

MySQL VARCHAR Truncation Exploit — Full Chain

  • Observation: MySQL ignores trailing spaces in VARCHAR comparisons but stores them distinctly — a mismatch between WHERE and INSERT.
  • Source audit: createUser() uses substr($usr, 0, 64); validUser() uses raw input; dumpData() uses trim($usr) — three inconsistent views of the same username.
  • Exploit (Burp Suite): POST username=natas28+57×space+x&password=password (65 chars). PHP truncates the 'x', leaving natas28 + 57 trailing spaces stored.
  • Result: Logged in as natas28 with my own password; dumpData() + trim() returned the original user's row — leaked the natas28 password (flag).
  • Defense: Use VARBINARY for usernames, trim input before comparison, reject whitespace-only differences, and never rely on MySQL's trailing-space semantics for auth.
📅 Jul 2026🏷️ Linux Privilege Escalation🔗 OverTheWire Bandit

Linux PrivEsc via Cron & SetUID Binaries

  • Observation: Multiple Bandit levels involve cron jobs running as root or setuid binaries that allow arbitrary command execution.
  • Exploit: Identified writable cron scripts, injected reverse shells, exploited nmap --interactive, and abused tar wildcard injection.
  • Outcome: Escalated from low-privilege user to root across multiple levels, capturing each flag.
  • Defense: Avoid setuid on custom scripts; sanitize cron PATH; never run tar with wildcards on untrusted directories.
Pillar 3 · How I Think Under Real Scenarios

Think-Aloud Walkthroughs

My methodology follows a repeatable loop: recon → hypothesize → test → pivot. Here's exactly how I approached two very different challenges.

Scenario · MySQL Truncation (Natas 27)

Step 1 — Read the source code

I noticed substr($usr, 0, 64) in createUser() and trim($usr) in dumpData() — an inconsistency. validUser() used raw input. Classic sign of a truncation bug.

Scenario · MySQL Truncation (Natas 27)

Step 2 — Form a hypothesis

"If I push a 65-char username past the 64-char limit, the 65th character gets chopped during INSERT. But MySQL's WHERE still matches the truncated value due to trailing-space insensitivity. I can create a duplicate user with my own password."

Scenario · MySQL Truncation (Natas 27)

Step 3 — Test, debug, pivot

Sent POST username=natas28+57spaces+x via Burp. User created. First login said "Wrong password" — I debugged via the CREATE response, then re-logged in as natas28: checkCredentials matched my fake user, dumpData() + trim() returned the original natas28's row. Flag captured.

Scenario · Linux Escalation (Bandit)

Step 1 — Recon

Ran ls -la, find / -perm -4000, checked /etc/crontab and writable directories. Found a setuid binary or a cron job running my user's script.

Scenario · Linux Escalation (Bandit)

Step 2 — Exploit & verify

Leveraged the setuid binary to execute commands as the target user, or modified the cron script to copy the next level's password. Verified with whoami and cat before moving on.
